# Design: poison-record-resilience

## Context

Indexer read paths deserialize whole responses strictly: `TreeDelta`, `WorkspacesResponse` and `InboxResponse` hold `Vec<IndexerEnvelope<T>>`, so one element that fails serde fails the response. The PDS read path (`list_collection`, used by seven listing sites including grants, keyrings, pairing cleanup, encryption-public-key resolution and the CLI cabinet tree build) skips unreadable records per-record; the two paths disagree and neither behavior is specified. SSE upsert events parse per-event but drop the whole event on a corrupt record, silently. Records are member-authored and the indexer relays them verbatim, so any member can produce a record the current client cannot parse — maliciously or by version skew, which in a federated workspace is normal operation.

The key-derivation transcript binds both the algorithm identifier and a schema version (`crates/opake-crypto`: `"opake-v{version}-{algo}-{tag}-{uri}-{recipient_did}"`), which makes version and algorithm skew cryptographically visible — and makes it essential that readers derive parameters from the record's declaration, not their own compile-time constants.

An independent adversarial review (2026-07-15) found the first draft's version gate incomplete (algorithm skew escaped it), the SSE path unspecified, and the `list_collection` policy change under-scoped; this revision incorporates its findings.

## Goals / Non-Goals

**Goals:**
- One specified policy for record degradation shared by every read surface — snapshots, deltas, listings, SSE upserts, PDS collection listing.
- A complete, single-axis understanding test: comparing `opakeVersion` covers schema shape AND cryptographic vocabulary, because vocabulary is pinned per version.
- Degradation a user can see and reason about: nothing silently vanishes, nothing relocates, every block carries an actionable message.
- Writes never build on state the client cannot fully understand; maintenance never deletes what it cannot read.
- Indexer refuses malformed and vocabulary-violating records at ingest without becoming an upgrade bottleneck.

**Non-Goals:**
- No UI redesign: clients get corrupt references, locked-record marks and placeholder state; presentation beyond a minimal badge/`-v` line is follow-up product work.
- No re-validation of already-indexed history at the indexer.
- No change to indexer-consistency's ordering contract (cross-cited, not modified). tree-chains gains one degradation requirement (unverifiable heads) — its authority rules are otherwise untouched.
- No schema v2: this change makes version skew survivable but introduces no new version.

## Decisions

**D1. Read-lenient, write-strict.** Read paths tolerate records they cannot fully understand, because denying the whole view to punish one record is a workspace-scale DoS with a legitimate everyday trigger. Write paths refuse to mutate a chain or keyring containing a link the client cannot fully understand — corrupt or future-version — because writing against partially-understood state clobbers or forks semantics the client cannot see. Maintenance is a write: healing never revokes a grant it cannot read.

**D2. Classification is a three-sentence rulebook, and the version peek comes first.** The classifier extracts `opakeVersion` from the raw value BEFORE any typed parse. Future-version records are judged by their version plus one structural check the client IS entitled to: the required-field floor of its own newest known schema (additive evolution guarantees every future record contains every past version's required fields). Floor present → locked; floor missing → corrupt regardless of the declared version — a claimed future version is a claim to more vocabulary, never an exemption from the past's requirements. Without the floor check, stamping a high version on garbage would launder 'corrupt' into a permanent, falsely-actionable 'needs-newer-client' lock (round-3 review finding). Then: can't parse it under a known version (including missing/mistyped `opakeVersion` — no serde default masking) → corrupt. Claims a known version N but uses vocabulary outside version N's cumulative set → corrupt (a rule-breaker, not a mystery). Envelope well-formed, version > supported → visible but locked: kept, marked needs-newer-client, mutation-gated, no typed parse required. The lenient deserializer emits corrupt references (`{uri, reason}`, URI when extractable) rather than bare counts — placeholder rendering and diagnostics need the URIs, not a tally.

**D3. Placeholder nodes for addressable corrupt containers.** When the envelope URI is known and records inside the member's authorized snapshot parent to it, tree building inserts an opaque placeholder (client-assigned display name, never attacker-controlled text) so children remain attached and visible. Placeholders are created only for elements the authorized snapshot references — degradation reporting must not become an out-of-scope disclosure channel. Position is established by the surviving references and moves only when they do; the degradation logic itself never relocates anything. Envelope-unparseable records have nothing to hang a node on: count-only. Placeholders derive from indexer-confirmed references, upholding indexer-consistency's confirmed-state-only projection contract. Rejected alternatives: dropping the subtree (scoped hide-my-colleagues'-work lever), reparenting orphans to root (files appear to move; confusion-attack primitive).

**D4. Chain links are not view records.** An authority walk that crosses a corrupt link cannot verify the head; the client rejects the head and falls back to the last verifiable state. Same posture as chain.rs mirror-validation today: integrity over liveness.

**D5. `opakeVersion` comparison is the complete understanding test.** Because vocabulary is pinned per version (D8), "is this record's version newer than mine" answers every skew question — schema shape and crypto alike. Future-version records stay visible but are presented as locked (their payload may be undecryptable by this client; display is client-assigned), and mutations against them are refused with an actionable "newer client required" message. The early-upgrader write-freeze this creates is accepted deliberately: one member's upgrade may block others' writes until they update, but nothing is lost or hidden, the remedy is one update, and the message says so — a self-explanatory block, not a mystery error. Rejected alternative: narrowing the gate per-link — the shared keyring is the first thing written new-style and every write wraps under it, so narrowing buys complexity without relief.

**D6. Ingest gate: structural validation for all, vocabulary enforcement for known versions.** The indexer validates every incoming `at.opake.*` record structurally against the newest lexicons it ships (additive evolution guarantees any well-formed version parses), and additionally enforces pinned vocabulary for versions it knows. Malformed or vocabulary-violating → refused: rejection, not deletion; the record stays on the author's PDS, matching the authority-enforcement precedent. Future versions pass structural checks only — no lock-step federation. Validation source of truth is the lexicon JSON plus the version-vocabulary table; no hand-maintained parallel schema. Client lenience stands regardless: the indexer is not a trusted party, and pre-gate history may contain poison.

**D7. Phasing.** Phase 1 (client resilience, D1-D5) unbricks the view and gates the public flip. Phase 2 (ingest gate, D6) is independent and may land after. Phase-1 tests must not depend on phase-2 behavior.

**D8. Additive fields, version-pinned vocabulary, breaking = new NSID.** Within a collection: schema changes are ignore-safe field additions only. Union variants, enum values and registry vocabularies are NOT ignore-safe — each schema version pins its exact permitted vocabulary, cumulatively (version N permits everything pinned at or below N), and a new value ships as a version bump plus vocabulary entry, inseparably. The vocabulary-bearing fields are a closed, enumerated list of value identifiers — key-wrap algo identifiers, content-encryption algo identifiers, encryption public-key algo identifiers, pairing KEM/cipher algo identifiers, and keyring member roles — and extending that list is itself a version bump. Union $type discriminants (keyWrapping.$type, document.encryption.$type) are explicitly NOT vocabulary: a $type tag selects a structure, and new structures take the NSID path per the honesty bound below. The version→vocabulary table lives as a language-neutral JSON artifact in the repo (single source of truth), embedded at build time by both opake-core (Rust `include_str!`) and the indexer (Elixir `@external_resource`), with a cross-language conformance test keeping the two consumers honest (the OPAKE_COLLECTIONS pattern). This closes the axis-split hole: crypto evolution cannot outrun the version gate because it travels *inside* it, and a version/vocabulary mismatch is detectable corruption rather than silent skew. Honesty bound: the vocabulary channel covers algorithms that fit the existing envelope shapes (identifier swap, same wire layout). A structurally different future scheme — a new KEM with a different ciphertext layout, a new keyWrapping variant — is a structural change and takes the expensive new-NSID path; vocabulary-pinning does not make all crypto evolution cheap, it makes identifier-level agility safe. Wire representations of registry values are open strings (the Rust layer parses unknown values; understanding is checked against the vocabulary table, not the type system). Changes expressible neither as ignore-safe additions nor vocabulary bumps take a new collection NSID — acknowledged as prohibitively expensive for identity-bearing collections (workspace identity is a keyring URI), which is deliberate: core collections are additive-forever in practice. Consequence: the v1 lexicons' required/optional markings are permanent; a pre-v1 lexicon audit is part of this change.

**D9. PDS lexicon validation as layer 0.** Opake lexicons mark all crypto-envelope fields required and are published for lexicon resolution (`_lexicon` DNS on opake.at — pre-existing, outside this repo), so conforming PDSes reject malformed writes at the source. Untrusted (authors control their PDS, `validate: false` exists) and merely accident-preventing. Three layers, distinct trust values: PDS write validation (honest-author accidents) → indexer ingest gate (network hygiene) → client lenient parse (the only trustless layer).

**D10. SSE parity.** A record arriving by SSE upsert produces the same client state as the same record arriving in a snapshot — corrupt handling, placeholder rules, future-version marking, workspace signals, all identical — and a corrupt record never terminates the stream. Without this, the same poison behaves differently depending on delivery timing, and the bootstrap-vs-stream distinction leaks into user-visible semantics.

**D11. Cryptographic parameters follow the record's declaration.** Unwrap derives its KDF transcript from the record's declared `opakeVersion` and algorithm identifier, never from the reader's compile-time constants. The declared values are bound into the transcript for domain separation and self-consistency — binding is NOT authentication; a writer chooses its declaration and computes the matching transcript, and implementations must not treat the declared version as attested. No downgrade exploit follows (forging a transcript over content you don't hold fails AEAD integrity), but the distinction matters to implementers. Threading the declared version into unwrap is a cross-cutting signature change touching every unwrap call site; partial threading (some sites record-derived, some compile-time) is the drift failure mode to guard against. Otherwise a well-formed, known-vocabulary record written by a newer client fails decryption for no protocol reason.

## Risks / Trade-offs

- **Lenient reads can mask real data loss.** Mitigated by mandatory corrupt references reaching the client surface, not just logs.
- **Placeholder existence-disclosure.** Bounded by the authorized-snapshot invariant (D3): placeholders and references are only created for elements the member's snapshot already contains; no new disclosure beyond what the envelope already exposes to members.
- **Write-strictness can wedge a workspace on a permanently-corrupt head** (departed author). Accepted: cleanup is the recovery story today; custody/re-homing (#19) owns the durable fix.
- **Early-upgrader write-freeze is routine, not exceptional.** Accepted per D5 with the actionable-message requirement; the freeze resolves the moment the user updates, and the message tells them exactly that.
- **Version bumps become more frequent** (every vocabulary addition). Accepted: versions are cheap integers, each bump is additive, and bumps double as an auditable protocol changelog.
- **Ingest gate adds schema knowledge to the indexer.** Bounded: structural validation against the shipped lexicon JSON plus a version-vocabulary table; no cryptographic or semantic validation moves server-side. No mature Elixir lexicon validator is known — a minimal validator over `at.opake.*` lexicons only is in scope.
- **Additive-forever is a permanent commitment for core collections.** The new-NSID escape hatch costs identity migration for keyring/directory, OAuth re-consent, and a dual-collection indexer era — effectively unusable there. Accepted with the rider: crypto agility travels through version-pinned vocabulary, and the pre-v1 lexicon audit is the one cheap moment to fix required/optional markings before they freeze.
- **`list_collection` policy change touches seven listing sites.** Managed by per-caller policy (D2 policy for user-facing collections incl. publicKey resolution; pairing keeps existing semantics) and caller-by-caller re-verification in tasks.
- **Version-vocabulary table drift across languages.** Mitigated by the single JSON artifact + cross-language conformance test (D8); hand-copying the table into Rust or Elixir constants is the failure mode the test exists to catch.
- **The declared-version decrypt test is mechanism-only until a v2 exists.** With only v1 defined, the cross-version unwrap test necessarily mocks a synthetic version; it asserts the plumbing (record-derived transcript parameters), not real-world v2 behavior. Named here so nobody mistakes it for coverage of an actual migration.

## Lexicon audit outcome (task 1.5)

Reviewed the `required` markings on every `at.opake.*` record and shared def against the additive-forever consequence (a required marking can never be removed once v1 ships). Result: clean. Every crypto-envelope field is required on its record — `keyWrapping` + `encryptedMetadata` (directory), `encryption` + `encryptedMetadata` (document), `wrappedKey` + `encryptedMetadata` (grant), `algo` + `members` + `encryptedMetadata` (keyring), the key/algo fields (publicKey, pairing). Vocabulary-bearing fields are required where they gate meaning (`wrappedKey.algo`, `keyringMember.role`). The required floors match the `RecordKind::required_floor` sets the client classifier enforces. No markings changed; the v1 lexicons are frozen as-is with the required set confirmed correct.
